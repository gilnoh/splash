# Splash on M1 Max: engine comparison and decision (2026-09-27)

Personal experiment note. Question: what is the fastest way to run Qwen3.8-27B on this
machine for long-context agent work (tool output, OCR, web sources appended turn by
turn; 50k typical, up to 200k)?

**Machine:** MacBook Pro M1 Max, 32-core GPU, 64 GB, macOS 26.6.2, Xcode 26.6.
**Baseline:** Ollama 0.34.4, `qwen3.8:27b-128k` (MLX engine, nvfp4).

## Decision

Use **Splash with the community M1/M2 kernels** (paperniuk's `apple7-m1-kernels`
branch), and maintain a personal fork that tracks upstream with the M1 patch on top.
It is the only engine that is clearly faster than Ollama at 50k on this machine, and
only on decode (1.4-1.7x). Prefill is the same on every engine at 50k, so the real
prefill fix is a different model (e.g. an MoE like Qwen3.6-35B-A3B) or newer
hardware. Until then, the M1 is what we have, and some maintenance cost for a 1.4-1.7x
decode gain is worth it.

## What exists (surveyed 2026-09-27)

Generic Apple Silicon engines:

- **oMLX** (jundot/omlx, ~22k stars): MLX server, continuous batching, SSD-tiered KV
  cache, native MTP. Works on M1.
- **MTPLX** (youssofal/MTPLX): uses the model's own MTP heads for exact speculative
  decoding; ships FP16 builds for M1/M2.
- **llama.cpp**: has an MTP flag, but one report found MTP made it slower on a Mac,
  and an open bug (ggml-org/llama.cpp#27623) drops decode from ~33 to ~1.4 tok/s past
  ~80k context on this model.

Engines built only for Qwen3.8-27B:

- **Splash** (incoai/splash, Apache-2.0): model-specific kernels, a trained DFlash 2
  draft model, and a memory plan built for this model. Officially needs M3 or newer.
- huangfcn/qwen3-27b-metal, jessestimpson/qwasar, rjohny55/q36, omnigeeker/qwen38-rs,
  ggluo/Qwen3.8-27B-MLX: smaller single-model engines. M1 is either untested,
  alpha-quality, or the engine is terminal-only. None was tried.

### Why upstream Splash refuses M1

Two checks in `runtime/metal/DeviceCapabilities.cpp`:

1. `apple_gpu_family_9_required` (M3+). This is Inco's policy, not a missing Metal
   API. The kernels are written for BF16, which M1 GPUs cannot compute natively, and
   they are tuned only for M3/M4/M5.
2. Placement-sparse buffers, queryable from macOS 26.4 (the KV cache reserves the full
   context's address space and commits pages only when used). M1 supports this.

Also: one split-K decode kernel reads other threadgroups' partial sums through a
non-coherent L1 cache and corrupts its output on M1. The community port fixes this
with `coherent(device)`.

The community port (incoai/splash#131, fork paperniuk/splash): FP32 and half-weight
register-matrix kernels for Apple7/8, with a separate kernel policy. The M3+ path is
unchanged apart from the `coherent(device)` declaration. Upstream had not responded
as of this date.

## Measurements

Build tested: `paperniuk/splash@5967821` (branch `apple7-m1-kernels`, based on Splash
1.0.2). Method: identical prompts for every engine, each with a unique nonce prefix
(no cache hits), 256 output tokens, reasoning off, temperature 0, one engine loaded at
a time. Prose = Gibson novels; code = Splash's own `runtime/` C++. Splash and Ollama
timings are server-side; oMLX and MTPLX are timed on the client.

**~50k tokens, quiet machine** (tok/s):

| Engine | Prefill, prose | Prefill, code | Decode, prose | Decode, code |
|---|---|---|---|---|
| Ollama 0.34.4 (nvfp4) | 72.5 | 75.0 | 11.2 | 10.1 |
| **Splash (M1 port)** | 75.4 | 75.5 | **15.5** | **17.3** |
| MTPLX 2.12.0 (Optimized-Speed-FP16) | 77.3 | 78.4 | 11.9 | 12.3 |
| oMLX 0.7.0rc1 (oQ4e + MTP) | 74.7 | 77.6 | 11.9 | 11.2 |

Prose prompt: 51k tokens; code prompt: 44k. A cold prompt takes ~10-11 min to the
first token on every engine.

**~2k tokens** (tok/s):

| Engine | Prefill | Decode |
|---|---|---|
| Ollama | 81 | 15.0 |
| **Splash** | **121** | **30.7** |
| MTPLX | 82 | 18.0 |
| oMLX | 89 | 18.6 |

The Splash and Ollama 2k figures come from a first round that may have overlapped a
CPU compile. That compile cost Splash ~20% at 50k (12.4 -> 15.5 decode once the
machine was idle) and Ollama less (9.8 -> 11.2).

Observations:

- Prefill at 50k is 72-78 tok/s on every engine. This looks like the limit of this
  machine for this model, not something an engine can fix.
- MTP gives oMLX and MTPLX ~1.2x at short context and almost nothing at 50k. oMLX's
  log showed draft acceptance falling to 67-75% at depth, and it kept pausing MTP.
  Splash's trained draft model keeps a 1.4-1.7x lead at depth.
- Our Splash numbers are ~60-70% of paperniuk's reported M1 Max results (25 tok/s
  decode at 51k). Their prompt set differs, and the cause is unresolved.

## Maintenance plan

paperniuk is one person working in short bursts (an oMLX experiment one week, an LM
Studio one the next), and upstream Splash moved 276 commits in 3 days. Relying on the
community fork alone will likely freeze at 1.0.x.

- Personal fork `gilnoh/splash`: `main` mirrors `incoai/main`; `gil/m1` carries the
  M1 patch as a rebased commit stack.
- Remotes: `upstream` = incoai, `m1` = paperniuk (reference: reuse their conflict
  resolutions when they exist).
- Rebase on upstream releases, not on every commit.
- Check every rebase before using it: `make test-engine`, a greedy reference-output
  check against a known-good build, and a short benchmark (2k/32k decode and prefill).
  If any step fails, keep the previous build.
- State on 2026-09-27: `gil/m1` = `m1/apple7-m1-kernels` (1.0.2 based). Merging onto
  upstream 1.1.0 conflicts in 13 files, all in kernel planning and dispatch
  (`ExecutionPlans`, `Linear`, `MoE`) and their tests; the new kernels apply cleanly.

## Prefix caching

Tested on the same build, default settings (context 256K, no memory cap), with an
agent-style conversation on a 32k prose base, 64 output tokens, temperature 0:

| Step | Prompt | From cache | Newly prefilled | Time to first token |
|---|---|---|---|---|
| A. Cold 32k | 32,147 | 0 | 32,147 | 365 s |
| B. Exact repeat | 32,147 | 32,128 | 19 | 0.6 s |
| C. + assistant reply + 4k tool output | 36,239 | 32,128 | 4,111 | 59 s |
| D. Unrelated short request in between | 17 | 0 | 17 | 0.4 s |
| E. Turn 3 (reply + short tool output) | 36,344 | 36,224 | 120 | 1.9 s |
| F. Edit at the start of the prompt | 32,152 | 0 | 32,152 | 371 s |

- **Correct:** B's greedy output is byte-identical to A's, so the cached path
  computes the same result. F rejects the cache after an early edit instead of reusing
  stale state.
- **Growing context:** each turn prefills only the newly appended tokens. Those run at
  ~70 tok/s at this depth, so 4k of new tool output costs about a minute rather than
  six. An unrelated request in between does not evict the conversation's cache (E).
- The cache works in 32-token pages (32,128 = 1,004 x 32). The last partial page
  and the assistant reply of the previous turn are prefilled again; that is small
  either way.
- **How long the cache lasts (from the code):** there is no TTL or keep-alive
  setting. `KvCache.cpp` evicts least-recently-used blocks only when space is needed.
  `MemoryGovernor.cpp` polls macOS memory pressure every 500 ms: at "warning" it frees
  enough to get back above its margin, at "critical" it drops everything evictable,
  and at "normal" it does nothing. The cache is process-local, so a server restart
  loses it (per DEVELOPMENT.md). Keep Splash running as a long-lived server, and
  don't load another large model (e.g. Ollama) next to it.
- Upstream 1.1.0 adds an SSD tier (`--max-cache-disk`, incoai/splash#3) that moves
  evicted pages to disk instead of discarding them, which helps with several long
  sessions. It is not in our 1.0.2-based build and comes with the first rebase.
  Its files are temporary and do not survive a restart either.
- Not tested: behaviour when several long sessions compete for memory.

## Update 2026-09-28: moved to Splash 1.1.0

Branch `gil/m1-1.1.0` (built and checked on this machine). `gil/m1` (1.0.2) is
unchanged and tagged `gil-m1-baseline` as the fallback.

### What the branch is

- paperniuk published a 1.1.0 port on 2026-09-27 at 20:44
  (`m1/apple7-m1-kernels-1.1`, release `1.1.0-m1`): 12 commits directly on the
  upstream `1.1.0` tag. It did not exist when the plan above was written. We
  used it as is, rather than rebasing our 10 commits ourselves; the 13 conflicts
  are already resolved and tested there. The one upstream commit after 1.1.0
  (`c64a578`) only changes the README and docs, and is not included.
- On top: this note, and `fix: bound isolated prefill commands on Apple7/8 only`.
- Beyond the 1.0.2 patch, the port adds: prefill split into GPU commands of
  about 5 s (macOS aborted long prefill commands on M1: 1.0.2-m1 failed at 176K
  in a long agent session), simdgroup-MMA kernels for GGUF models and the
  vision encoder, and an RMS-norm fix needed by `make test-engine-metal` on M1.
  A residency-set change and its revert cancel out.

### Decisions on the M3+ (Apple9) path

The M3+ path should stay as upstream ships it. Four changes in the port are not
gated to Apple7/8:

- **5 s prefill bound** (Scheduler): on for every GPU by default. It changes
  M3+ behaviour, so our extra commit enables it only below GPU family 9
  (in `Bootstrap.mm`, where the device is known). `--prefill-mode full` still
  turns it off on M1; on M3+ the flag has no effect.
- **`max_total_threads_per_threadgroup(1024)` on the staged RMS norm**: kept.
  The dispatch already uses 1024 threads everywhere; the attribute only stops
  shader validation on M1 lowering the limit to 832. Not verifiable on M3+ here.
- **`dequant32` split into `dequant_chunk`** (GGUF staged tiles) and **the
  verify-tile struct moved to a header**: kept. Both are code motion with the
  same arithmetic.
- The `coherent(device)` fix on split-K partials needs nothing: upstream 1.1.0
  already has it in `linear_q4_sgmatrix.metal`.

### Check results (`dev/m1-verify/verify.sh`, M1 Max, quiet machine)

| Check | 1.0.2 (`gil/m1`) | 1.1.0 (`gil/m1-1.1.0`) |
|---|---|---|
| `make test-engine` (Metal suites on family 7) | pass | pass |
| Kernel policy log line | family 7, 32 cores | family 7, 32 cores |
| Greedy outputs (7 prompts, 128 tokens) | reference | 4 identical, 3 differ (below) |
| Prefill ~2k prose / code (tok/s) | 111 / 113 | 108 / 111 |
| Prefill ~32k prose / code | 88 / 90 | 91 / 94 |
| Decode ~2k prose / code | 34.7 / 31.9 | 34.0 / 31.3 |
| Decode at 32k, mean of 8 questions | 16.9 | 17.1 |
| Draft acceptance at 32k, 8 questions | 25.8% | 26.4% |
| Time per verify step at 32k | 163.9 ms | 163.7 ms |
| Prefix cache (steps A-F above) | pass | pass |
| SSD tier (`--max-cache-disk`) | n/a | pass |
| ~114K prompt without engine failure | not run | pass |

- **Greedy differences** start at tokens 7, 12 and 118 of 128, at word choices
  that both builds make fluently ("not peaceful, but" vs "not peaceful; it
  was"). Cause: upstream `fca1a8b` ("Keep all logits in fp32"). 1.0.2 picked
  the greedy token from logits rounded to bf16, which merges near-ties;
  upstream measured the bf16 argmax agreeing with the fp32 one only ~99% of the
  time on this model. Over ~800 generated tokens several flips are expected,
  and each changes the rest of that output. The kernel tests against fp32 CPU
  references pass, and the cached-path check (identical output from cache)
  passes on 1.1.0.
- **SSD tier**: with `--max-memory 20G` (context 53K) a 16K prompt was pushed to
  disk after two others (562 MB demoted); asking it again restored it from SSD
  with a time to first token of 0.5 s instead of 158 s and the same output.
- **~114K prompt**: 113,966 tokens prefilled at 60 tok/s (32 min to the first
  token), then decoded at 9.5 tok/s with 22% draft acceptance. The 5 s prefill
  bound is what should keep macOS from aborting this; past ~176K is untested.

### Benchmark lesson: one long prompt does not measure decode

The first comparison showed decode at 32k 12% slower on 1.1.0. It was not the
build. Decode speed with the draft model is (tokens per verify step) / (time
per step). The time per step was identical on both builds (163-165 ms), while
the tokens per step depend on how well the draft predicts that particular
continuation. Across eight questions of the same cached 32k context, decode
ranged from 14.8 to 18.9 tok/s on each build, and 1.1.0 came out slightly
ahead on average. Because 1.1.0's fp32 logits produce a different continuation
of the same prompt, a single prompt compares two different texts.

So `verify.sh` now judges decode at depth on the eight-question mean and on
the time per verify step, and reports single-prompt 32k decode for information
only. The same caveat applies to the 50k decode figures in the tables above:
each is one continuation, roughly +-10%.

### Maintenance plan, revised

- On an upstream release, first `git fetch m1`: if paperniuk has ported it,
  start from their branch, as this time. Rebase ourselves only if they go quiet.
- Check every candidate with
  `dev/m1-verify/verify.sh --reference <known-good results> --out <dir> --long`,
  after recording the known-good build with `--record`. Greedy differences need
  a named cause; performance must hold within 5% on the gated rows.
